Repeated work means repeating training since the last saved state. You are right about the quantity that matters: T is the training time between checkpoints. Five minutes was only the result of my hypothetical T = 10 minutes; it was not an estimate for real workloads.

If we save every N iterations and an iteration takes s minutes, then T = N × s. With interruptions spread roughly uniformly through that interval, the average training to repeat is approximately T/2. This is time to recompute the lost updates, assuming the resumed job runs at the same speed. It is separate from checkpoint writing and process restart time.

The crucial comparison: an ordinary complete training checkpoint can also be triggered by the warning. If it fits within W, it too preserves the latest completed update. Then snapshotting earns its value through easier application support or a better total save-and-restart time; the avoided T/2 loss is no longer its unique advantage.

A has spot; B requests on-demand. Who waits and pays?

Jarvis's scheduler—the software assigning machines to jobs—can decide to reclaim A's GPU for B. This is a provider-controlled decision, rather than a GPU unexpectedly breaking. B's request does not itself define a mandatory warning duration or billing rule.

A remains allocated while capture uses its GPU. B can use that same GPU only after release and any required cleanup/setup. Jarvis might bill A through release, waive that time, or offer a snapshot fee. Charging B while it waits is also a product-policy decision; we have not established Jarvis's actual policy. Counting both customers as using the same exclusive GPU at once would overstate utilization.

The provider must account for A's RAM/storage use and delayed service to B. It might keep A's CPU process and staged GPU data in RAM while B uses the GPU, if the platform supports that arrangement. That offers quick planned pause/resume but does not protect against losing the host.

Jarvis documents reclaimable spot capacity. A two-minute warning is an AWS example, delivered best-effort for stop/terminate; it is not a verified Jarvis guarantee. Jarvis spot description; AWS warning behavior.

What is a snapshot, physically? Files containing saved memory bytes plus records explaining how to reconstruct a running process. “CPU snapshot” here means that process's execution state, not the entire CPU chip or every application on the server.

Consider step = 20, a Python tensor object, and its GPU allocation. The counter and object live in host RAM. The tensor object contains a pointer—an address referring to its GPU data. Saving the numbers alone leaves out both that relationship and where execution should continue.

Linux side

Memory containing Python objects and function stacks; each thread's registers, including its next instruction; memory mappings; open-file references and positions; supported timers, pipes and sockets.

CUDA side

GPU allocations and their contents; their addresses; the CUDA context—the process's GPU environment; streams—ordered queues of work; and related CUDA objects.

Why can't CRIU put all the memory back immediately?

Each process sees its own numbered memory addresses. A memory mapping tells Linux which address range refers to which memory or file. A saved pointer still refers to the old address, so restoring bytes somewhere else would not be enough. But the process doing the rebuilding already has code and data at some of those addresses.

A stack holds a thread's active function calls and local data. CRIU first loads saved memory into temporary mappings. A small restorer, placed outside both memory layouts, then moves memory to its required addresses. It can replace the old layout without deleting the instructions it is currently executing. Memory restoration; restorer context.

“Restore” is several steps. Resuming the program is last.

Restoration starts when CRIU begins rebuilding processes. The final action is to hand control back to the saved application instructions. Before that handoff:

  • Memory must be at the right addresses. Otherwise a saved pointer or stack pointer could refer to the wrong bytes.
  • The remaining threads are recreated late. Their stacks must be ready; creating them late also avoids keeping extra threads parked during memory replacement.
  • Timers are restored late. Starting them early could let them expire while reconstruction is still underway.
  • Permissions are restored late. CRIU may need privileges to finish setup. Giving those up too early could prevent it from completing the job.

Why CRIU orders these operations this way.

At the handoff, saved CPU registers—small values held by the CPU, including the stack address and next instruction address—are restored. Linux's rt_sigreturn mechanism can restore this execution context. The next instruction can then use the reconstructed process. How that CPU handoff works.

Restoring an open-file reference does not recreate every file's contents. The executable, libraries, datasets and external services must remain available or be provided separately. Snapshotting one process does not roll back the outside world. External resources.

Why NVIDIA is needed: Linux can describe a reference to a GPU device, but ordinary process memory does not contain everything needed to reconstruct that device's private state. NVIDIA's driver supplies that missing capability. The following is the logical sequence; the plugin coordinates the actual thread stopping and helper execution.

flowchart TD
 A["Finish update 20 and wait"] --> B["Block new CUDA changes; finish submitted GPU work"]
 B --> C["Copy GPU memory into driver-managed host RAM"]
 C --> D["Release this process's GPU resources"]
 D --> E["CRIU captures Linux state plus staged GPU data"]
 E --> F["Complete files on storage that survives removal"]
 F --> G["Original process gone"]
 G --> H["CRIU rebuilds Linux process"]
 H --> I["NVIDIA rebuilds GPU mappings and objects; copies bytes back"]
 I --> J["Unlock CUDA; release wait; execute update 21"]

NVIDIA restores GPU virtual addresses so saved pointers still refer to the right data; the physical memory chips or locations need not be identical. Submitted GPU work completes before capture: this mechanism does not preserve a kernel halfway through an instruction. NVIDIA's GPU suspension alone leaves CPU threads able to run, which is why coordination matters. NVIDIA's capture/restore sequence.

The subtle part: frozen threads and a running helper

A fully frozen process cannot execute NVIDIA's helper work. The plugin obtains the CUDA restore-thread ID, temporarily resumes that thread for device checkpoint/restore, then stops it again as required. It keeps ordinary application execution coordinated with those operations.

In the inspected source, follow cuda_plugin_pause_devices(), cuda_plugin_checkpoint_devices(), resume_restore_thread(), and cuda_plugin_resume_devices_late(). The last hook restores and unlocks CUDA. Our script must not duplicate those operations when the plugin owns them.

The same source disables CUDA handling for CRIU pre-dump. CPU support for preliminary memory copies therefore does not establish incremental GPU capture. CUDA plugin source.

We can inspect this coordination and the documented driver contract. We should not claim to know every private driver record or its byte layout from those sources.

Follow the bytes and the time. For an illustrative uncompressed snapshot, assume G = 16 GB of GPU data, H = 4 GB of CPU data to capture, GPU→RAM transfer = 12 GB/s, and completed storage writes = 1 GB/s.

GPU→RAM takes about 16/12 = 1.33 seconds. Writing roughly H + G = 20 GB takes 20 seconds. A sequential copy-and-write estimate is therefore 21.33 seconds, plus waiting, metadata and other overhead. These are assumed rates, not measurements.

Host RAM needs room for its existing workload plus roughly G of staged GPU data, with additional headroom for CRIU and buffering. Image size need not equal measured RAM + VRAM: shared/file-backed pages, cached allocations and encoding affect it.

Two clocks: time until A releases the GPU tells us when B might start using it; time until the image reaches surviving storage tells us when losing A's host is safe. Storage completion can happen later. Merely returning from a buffered file write does not prove durable storage.

Challenges worth understanding before implementation
  • Long GPU work: draining already-submitted operations can consume the warning window.
  • Memory headroom: enough VRAM does not imply enough host RAM for staging.
  • Unsupported memory sharing: the current NVIDIA README excludes UVM, automatically managed CPU/GPU memory, and specified IPC sharing APIs. Support depends on driver version; later features cannot be assumed on our recorded 580 host.
  • Restore compatibility: available RAM/VRAM, libraries, Linux permissions and GPU compatibility matter. The documented GPU remapping API requires the same chip type and enough memory; arbitrary L4→H100 migration is not our claim.
  • Failures outside the process: disk loss, remote connections, and multi-process GPU communication need additional coordination.
