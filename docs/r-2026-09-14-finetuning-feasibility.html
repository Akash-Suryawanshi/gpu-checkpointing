The planned LoRA experiment is technically feasible enough to proceed.

A live test restored a PyTorch GPU process from disk after the original exited.

What can be concluded

“There should be no fundamental obstacle” is a reasonable hypothesis for the small, ordinary LoRA configuration. “There are no blockers” is stronger than the evidence supports. Published systems have restored language-model training, and the new local experiment demonstrates complete CPU/GPU process restoration on the existing server. However, neither proves correct continuation of every optimizer, allocator, data loader, or fine-tuning framework.

The configuration assessed is the one in single-gpu-finetuning-research.md: Qwen2.5-0.5B, rank-8 LoRA on query/value projections, FP32, ordinary AdamW, one process, short local tokenized examples, eager execution, and a pause after update 20. “Complete” means ending the original process and resuming all required training state from a process image—not merely loading adapter weights.

A correction to the earlier recommendation: current DMTCP support is not limited to the historical CRAC prototype. DMTCP v4.2.0 introduced a native NVIDIA CUDA checkpoint plugin on June 26, 2026. Subsequent maintenance commits contain important fixes. This creates a concrete alternative to CRIU on a restricted instance. DMTCP release; tested maintenance revision.

How the alternative works

DMTCP starts the application with checkpointing support loaded into it. It can save and rebuild the process without the privileged external inspection used by CRIU. This requires launching the workload through DMTCP from the beginning; it is not a universal attach-to-any-running-process interface. DMTCP workflow.

Prepare CUDA
Block new GPU work
Move GPU state to CPU RAM
→
Save the process
DMTCP captures CPU state
Write the process image
→
Restore
Rebuild the CPU process
Restore CUDA and continue

The CUDA driver still handles GPU state. DMTCP replaces the CPU checkpointing layer.

The pinned plugin calls NVIDIA’s checkpoint operation before stopping application threads, allowing the driver’s helper threads to finish. During restart it restores CUDA after the CPU threads can run again. The GPU helper needs those threads for communication; stopping them throughout restoration can prevent progress. The maintenance revision explicitly coordinates this with DMTCP_EVENT_RUNNING_AFTER. Pinned plugin implementation.

The build used commit b175bb5ccadd2f02d11cf052f586d2d9ac62ad53, dated September 7, 2026. This contains fixes absent from the initial 4.2.0 release, including changes relevant to CUDA helper threads and PyTorch memory mappings. The exact commit is important; the default development branch and the initial release are not interchangeable.

The shared-memory warning deserves a precise interpretation

DMTCP does not simply omit the warned /dev/zero (deleted) regions. Its source saves their contents and restores them as private anonymous memory. The bytes survive, but a sharing relationship may not. This can preserve behavior for a buffer used only within one process; it can fail when another process or a second mapping must refer to the same physical pages. Threads within one process still share its address space. Memory-saving implementation.

The pre-checkpoint map listing contained four writable shared regions of 2 MiB each with distinct backing identities. Their ownership and any driver-side sharing assumptions have not been established. No documented CUDA-specific blanket exemption was found. Passing a tensor check is encouraging, but it does not settle every use of those regions.

The io_uring case is different: its memory depends on a kernel-managed object used for asynchronous I/O. DMTCP’s pinned source warns that restoring the bytes does not recreate that object. Such a warning should stop acceptance of that workload. Separate warning branches.

LoRA is a good baseline; QLoRA needs another gate

NVIDIA’s documented restrictions still apply when DMTCP calls the same driver API. The inspected NVIDIA revision excludes UVM managed memory and specified IPC mechanisms. Its newer legacy CUDA IPC support belongs to driver 610, not the installed 595 series. Changing the CPU snapshot tool does not add unsupported GPU capabilities. Pinned NVIDIA feature and limitation list.

In bitsandbytes 0.49.2, the paged optimizer path uses managed buffers for sufficiently large parameter tensors; its native allocator calls cudaMallocManaged. This is an identifiable incompatibility, not a vague concern about quantization. Four-bit base weights with an ordinary optimizer are a different configuration and require their own experiment. Check after Adam state exists, not just after model loading. Optimizer allocation path; Managed allocator.

The current PyTorch allocator reports native, with no allocator environment override. Its cache is not the same thing as managed memory. There is no basis for declaring every alternative allocator or CUDA graph unsupported; retain the simple native/eager setup until the baseline works, then test one additional feature at a time. PyTorch 2.11 CUDA memory documentation.

The large frozen base still exists inside a process snapshot. An application-level adapter checkpoint can omit it and reload a fixed revision later. Consequently, successful snapshotting does not automatically mean faster or smaller checkpointing than a complete LoRA training-state save. PEFT checkpoint format.

What the wider evidence establishes

Training snapshots are already demonstrated in primary research. CRIUgpu evaluates GPT-2 and Llama training. Its single-H100 Llama 3.1 8B result reports a 77.40-second checkpoint and 38.83-second restore. That supports feasibility of preserving a training process, but its hardware and software differ from this L4 experiment. CRIUgpu, February 2025, Table 2.

The EuroMLSys 2026 CRIU-LZ4 paper explicitly evaluates supervised fine-tuning on a B200 with CRIU 4.2, driver 590.48 and CUDA 13.1. It also shows that compression can increase pause time even while reducing image size. Its fine-tuning recipe is not specified sufficiently to certify this exact LoRA configuration. These papers demonstrate that the objective is realistic; they do not replace local correctness checks. CRIU-LZ4, §5.3 and Figure 9.

Commercial cold-start snapshots offer additional engineering precedent, but initialized inference workers are a different acceptance target. A successful worker startup does not show that optimizer moments, the next batch and subsequent training updates were preserved. The most relevant new evidence here is the native DMTCP plugin and its observed process-restoration result.

What is required before calling fine-tuning verified

The next experiment should keep the documented model and simple training loop. Avoid adding TRL, distributed initialization, remote tracking or data-loader subprocesses at this stage. Those are scope controls, not claims that these features can never work.

  1. Establish a reproducible reference. Pin model, tokenizer, data, packages and driver. Train twice without interruption and establish whether the chosen operations produce matching updates. Disable dropout initially; otherwise ordinary nondeterminism can be confused with a restore error. PyTorch reproducibility guidance.
  2. Capture after a completed update. At update 20, complete backward, AdamW, scheduler handling and gradient clearing; finish GPU work and wait at the explicit gate. Adam’s state must already be initialized.
  3. Save a DMTCP image and end the original. Wait for the completed image, record the real Linux PID’s exit, and sync the image. Run job B before restoring A. Do not use an application checkpoint as the process restore input.
  4. Check the exact state before update 21. Compare trainable tensors, optimizer tensors and step counters, learning-rate state, CPU/CUDA random generators and next batch position. Confirm model identity and configuration too. The diagnostic copies used for comparison must not become a hidden restore source.
  5. Compare the continuation through update 25. Require matching losses and updated parameters under the established deterministic setup. Exercise dropout in a follow-up so random-state restoration is tested by behavior, not merely a saved hash.
  6. Repeat the lifecycle and investigate warnings. Test a second checkpoint/restore cycle and normal exit. Attribute the shared-memory mappings and check required sharing behavior; a successful numerical check alone does not make unsupported-resource warnings disappear.

Decision: proceed with the small LoRA validation on the existing instance using pinned DMTCP plus the CUDA plugin. Treat it as an acceptance experiment with the shared-memory qualification still open. There is now direct evidence that a provider permission change is not necessary for the basic CPU/GPU restoration mechanism here.

What changes for actual spot recovery

The completed image and required external files must survive removal of the original instance. Local filesystem sync establishes a local write boundary; it does not establish the provider’s volume-retention policy. A replacement host must also have compatible GPU hardware, driver, libraries and filesystem resources.

Migration is a separate gate from same-host restoration. NVIDIA’s API imposes GPU compatibility and memory requirements, and newer 595-series release notes contain a restore-related device-information fix. That is a reason to validate migration explicitly, not evidence that this same-device experiment failed. CUDA checkpoint API; 595.91.07 fixes.

A checkpoint-on-warning scheme also needs enough warning time for the entire durable save. A sudden failure cannot trigger a successful capture after the state has already disappeared. This remains true with either DMTCP or CRIU.

Reproducing the build and avoiding the setup traps

The original v4.2.0 tag lacked later fixes and its CUDA test Makefile. The tested checkout uses maintenance commit b175bb5ccadd2f02d11cf052f586d2d9ac62ad53 and ./configure --disable-prgname-prefix. Its directory is named dmtcp-4.2.0 for historical reasons; the Git commit is authoritative.

The system nvcc is 12.6, while PyTorch ships CUDA 13.0 runtime components. The initial plugin compilation failed because the 12.6 headers did not declare the required checkpoint types. CUDA 13 runtime headers alone then exposed a missing CRT header dependency. Matching development files were installed into isolated tools directories, without replacing the active Python environment:

nvidia-cuda-runtime == 13.0.96
nvidia-cuda-nvcc    == 13.0.88
nvidia-cuda-crt     == 13.0.88

The plugin was built with the CUDA 13 runtime and CRT include paths and linked to the installed libcuda.so.1. The DMTCP source was not locally patched. The build’s version banner still reported the 12.6 nvcc on PATH; the actual include paths in the compilation command identify the headers used.

The probe used fresh private coordinator ports, a readiness/release handshake, explicit process-exit checks and image finalization checks. The first CPU attempt incorrectly assumed the blocking command implied a finalized image; that controller assumption was corrected before the successful second attempt. Coordinator logs include environment information, so raw logs and images remain outside Git; the report contains only focused evidence.
