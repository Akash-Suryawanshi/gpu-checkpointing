GPU snapshotting, step by step

A snapshot lets a running program become saved files, then become a running program again.
GPU training keeps information in ordinary memory and GPU memory.
NVIDIA brings the GPU part into ordinary memory; CRIU saves the process.
Our small experiment: train 20 steps, save, restore, then train 5 more.

1. What must survive?

A program is instructions. A process is those instructions running with their current information. That information is its state.

CPU · Runs the Python program

Ordinary memory · RAM

“I have finished step 20.”
“This is the next batch.”
“This is where execution continues.”

Python objects, random-generator state, and references to open files also matter.

GPU · Does the tensor calculations

GPU memory · VRAM

The model’s learned numbers.
The optimizer’s accumulated history.
The input and working tensors.

The NVIDIA driver also manages records of the process’s GPU resources.

Both halves must describe the same point in the work. A counter saying “step 20” beside weights from step 19 would be inconsistent.

Why aren't the weights enough?

A momentum optimizer remembers earlier updates. Identical weights with different momentum can take a different next step. The next batch and random-generator state can change the result too.

An application checkpoint, such as a dictionary written with torch.save, saves values chosen by the code. A new program loads them and rebuilds training.

A process checkpoint reconstructs the running program. The platform saves its execution state. Our demo still adds a cooperative waiting point to make the experiment easy to observe.

The GPU words, translated

CUDA: NVIDIA’s software interface for GPU computation.
Driver: software managing access to the GPU.
Context: the process’s GPU working environment.
Kernel: a function running on the GPU.
Stream: an ordered sequence of GPU operations.
Event: a marker of GPU progress.

One training step usually launches many kernels. Tensor bytes are only part of the state that must survive.

The bridge

GPU → RAM → disk. Then disk → RAM → GPU.
RAM stages the GPU copy. Disk holds the checkpoint after the original process ends. The tools also save and rebuild resource records.

Why two tools? CRIU saves supported Linux process resources. NVIDIA’s private GPU state needs NVIDIA’s help before CRIU can capture it. CRIU’s explanation.

01 · Stop changes and finish submitted work

Why: copying changing data risks an inconsistent snapshot.

How: block CUDA calls that change GPU state, then finish submitted work. A kernel completes; its half-finished computation is not captured.

Our loop finishes step 20, reports state, and waits for an explicit release. This chosen pause point keeps our comparison simple.

02 · Bring GPU state into RAM

Why: make GPU state available for process capture.

How: NVIDIA copies device memory into driver-managed host memory and releases the process’s GPU resources.

CPU threads are not frozen by this operation. Our explicit wait keeps training from advancing.

03 · Save the process to disk

Why: a copy in RAM disappears if the process or host is lost.

How: CRIU freezes the process and writes checkpoint files, including its memory and staged GPU data. In our experiment the original process must end after a successful dump.

“Image files” means saved process data, not photographs. This does not back up every file on the machine.

04 · Rebuild, reconnect, continue

Why: saved bytes need a process and working GPU resources again.

How: CRIU rebuilds the process. NVIDIA restores GPU memory, mappings, and CUDA objects, then unblocks CUDA calls.

Our loop checks its restored state before step 21. It does not reload the tensors with torch.load.

The sequence follows NVIDIA’s suspend/restore description. The step-20 waiting point is our reviewed demo design.

Why restore the original memory addresses?

The CPU holds pointers—addresses identifying GPU data. Restoring the original GPU virtual addresses keeps those saved references meaningful. Otherwise they could point to the wrong place. NVIDIA’s restore behavior.

Did the saved state return?

B20 = R20

Require exact matching tensor fingerprints before another update. Also check the step, input position, and random-generator state used by the loop.

Did training continue correctly?

A25 = B25

Target equality under the same deterministic setup. Compare A20 with B20 too, to confirm both runs reached the same state before capture.

What is a fingerprint?

A digest is a short fingerprint calculated from tensor bytes. Matching digests strongly support byte equality for the data checked; they do not prove that every process resource is correct.

A mismatched digest cannot measure closeness. If we allow rounding differences at step 25, compare actual values and choose a tolerance beforehand.

A fixed seed alone does not guarantee repeatable GPU results; deterministic operations and the same environment matter too. PyTorch guidance.

4. Why useful, why difficult?

A GPU cloud wants to reassign occupied GPUs without discarding training progress. Checkpointing supplies a mechanism: save, release, restore later. Migration and recovery after failures are further uses requiring extra coordination. NVIDIA’s use cases.

High return for our small POC

One process reveals the CPU/GPU split, resource release, and correctness checks. A failure can identify a concrete platform restriction.

More effort beyond it

Multiple workers, live connections, different hosts, GPU sharing, and automatic scheduling introduce separate problems. They stay outside this experiment.

Time and size: what costs us?

Our planning model is wait for work + copy GPU bytes to RAM + write the process image. More saved data generally needs more copying, RAM, and disk space.

For intuition only: 8 GB at an assumed effective 16 GB/s takes 0.5 seconds for that one copy. This is not a prediction of total checkpoint time. We measure our own result; a tiny demo cannot establish large-model performance.

Five boundaries to remember
  1. Kernels finish first. A long-running kernel delays capture.
  2. GPU suspend alone is not a disk checkpoint. Its staged state still depends on the CPU process.
  3. Some workloads remain unsupported. CUDA managed memory, also called UVM, is one documented limit. Some driver failures can leave the process unhealthy. NVIDIA limits.
  4. Restore needs compatibility. NVIDIA’s migration API requires the same GPU chip type and enough memory. Our demo uses the same host and GPU. API requirements.
  5. The outside world keeps moving. External files and messages do not automatically rewind; remote services can time out.

Ordinary PyTorch memory caching is different from CUDA managed memory. The earlier brief conflated them. Cached allocations alone do not rule out our POC. PyTorch memory management.

Yesterday's Jarvis pause is different evidence

The dashboard pause retained files under /home. That does not establish that a running Python process and GPU tensors survived. Our experiment must demonstrate that separately.

Full process restore demonstrated, GPU pause/resume only, and environment blocked are three different outcomes. Only the first meets the complete POC goal.

One picture to carry forward

Finish submitted work.
Bring GPU state into RAM.
Save the process to disk.
Rebuild both halves and continue.

Recall check · Why do we need both tools?

NVIDIA handles GPU state that ordinary Linux process tools cannot reconstruct. CRIU saves and rebuilds the process containing that staged GPU state. Together, on a supported setup, they can preserve the running job.
